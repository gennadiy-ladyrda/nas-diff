# DECISION-01

## 1. Задача
- Краткое название: Правила выбора primary и пользовательские решения
- Цель (что должно измениться в системе): Реализовать scoring для auto-primary и сохранение решений пользователя по группам.
- Ожидаемый результат в 1-2 предложениях: Для каждой группы есть рекомендованный файл для сохранения и API для ручной корректировки.

## 2. Scope
- Входит в задачу: scoring-алгоритм, `user_decisions`, API сохранения решения.
- Не входит в задачу: Физическое выполнение file actions.

## 3. Контекст
- Связанные документы/файлы: `docs/specification.md` FR-5, правила scoring (раздел 9), `database/schema.sql`.
- Текущие ограничения окружения (DSM6, Docker, пути NAS и т.д.): Один пользователь без ролевой модели.
- Зависимости/интеграции: exact/similar group services.

## 4. Требования
- Функциональные требования: Расчет `keep_score`, установка `is_primary`, сохранение `keep/trash/delete/ignore`.
- Нефункциональные требования (производительность, безопасность, UX): Повторяемый scoring; прозрачные причины выбора (`reason`).
- Ограничения по безопасности данных: Решения не должны автоматически запускать удаление.

## 5. Критерии приемки
1. Для группы всегда определен ровно один `primary` по умолчанию.
2. Пользователь может изменить решение и получить консистентное состояние.
3. Решения сохраняются и используются последующими action batch.

## 6. Проверки и тесты
- Какие проверки обязательны: Инвариант `1 primary per group`.
- Какие тесты нужно запустить: Unit tests scoring + integration tests decision persistence.
- Что считается успешной валидацией: Повторный расчет не ломает ручные решения.

## 7. Риски
- Основные риски: Конфликт между авто-оценкой и пользовательским выбором.
- Что делать при отклонении/ошибке: Приоритет ручного решения, логирование override.

## 8. Уровень неопределенности
Оценка `U = (R + T + D + S) / 4`:
- `R` (requirements): 0.06
- `T` (technical): 0.08
- `D` (data/environment): 0.07
- `S` (safety impact): 0.06
- Итог `U`: 0.07

Если `U > 0.1`, перед реализацией нужны уточнения.

## 9. Формат результата
- Какие артефакты ожидаются (код, конфиги, docs): decision engine, API route, тесты.
- Какой отчет нужен в финале: примеры групп до/после ручного решения.
