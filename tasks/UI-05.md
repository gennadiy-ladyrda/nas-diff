# UI-05

## 1. Задача
- Краткое название: Simple Scan — автоподстановка последнего каталога и режима
- Цель (что должно измениться в системе): Упростить повторные ручные сканы: в `Simple Scan` по умолчанию подставлять последний каталог и `scan mode`, использованные в последнем обработанном job.
- Ожидаемый результат в 1-2 предложениях: При открытии `Simple Scan` оператор сразу видит актуальные значения пути и режима из последнего job и может запускать следующий скан без ручного повторного ввода.

## 2. Scope
- Входит в задачу: Определение источника "последнего job", автозаполнение `Directory path` и `Scan mode`, fallback-логика при пустой истории.
- Не входит в задачу: Изменение backend-модели job и отказ от job-парадигмы.

## 3. Контекст
- Связанные документы/файлы: `frontend/src/pages/DashboardPage.jsx`, `frontend/src/App.jsx`, `frontend/src/api/client.js`, `docs/specification.md`.
- Текущие ограничения окружения (DSM6, Docker, пути NAS и т.д.): Single-user, `NAS_MOUNT_PATH=/nas`, path validation остается backend-side.
- Зависимости/интеграции: API-03 (`GET /scan/jobs` + `GET /scan/jobs/{job_id}`), UI-06 (default route на Simple Scan).

## 4. Требования
- Функциональные требования:
  - При загрузке `Simple Scan` получать последний job по `requested_at desc`.
  - Подставлять `Scan mode` из последнего job.
  - Подставлять путь каталога из roots, связанных с последним job (при наличии нескольких — брать первый в стабильном порядке и явно показывать, что root выбран автоматически).
  - Если jobs отсутствуют, использовать fallback: последнее локально сохраненное значение (`localStorage`) или дефолт `/nas/photo` и `both`.
  - После успешного старта нового скана обновлять "последние значения".
- Нефункциональные требования (производительность, безопасность, UX): Автоподстановка не должна блокировать ручное редактирование полей.
- Ограничения по безопасности данных: Никаких файловых действий; только заполнение полей запуска.

## 5. Критерии приемки
1. `Simple Scan` открывается с предзаполненными полями из последнего обработанного job.
2. При отсутствии job история не ломает экран, корректно применяется fallback.
3. Оператор может изменить значения вручную и запустить scan как раньше.

## 6. Проверки и тесты
- Какие проверки обязательны: Component tests для `Simple Scan` (with/without last job).
- Какие тесты нужно запустить: `vitest` по dashboard/simple сценариям + smoke ручной проверки в браузере.
- Что считается успешной валидацией: Поля предзаполняются детерминированно, запуск scan остается рабочим.

## 7. Риски
- Основные риски: Некорректный выбор пути при job с несколькими roots.
- Что делать при отклонении/ошибке: Явно документировать правило выбора root + показывать оператору выбранный путь до запуска.

## 8. Уровень неопределенности
Оценка `U = (R + T + D + S) / 4`:

- Итог `U`: 0.08

## 9. Формат результата
- Какие артефакты ожидаются (код, конфиги, docs): Изменения `Simple Scan` UI + tests + обновление поведения в `docs/specification.md`.
- Какой отчет нужен в финале: Перечень fallback-правил и результаты тестов автоподстановки.
