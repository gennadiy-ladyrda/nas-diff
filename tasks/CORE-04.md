# CORE-04

## 1. Задача
- Краткое название: Оптимизация чтения файлов в scan pipeline
- Цель (что должно измениться в системе): Уменьшить избыточное чтение файлов при сканировании и хешировании, сохранив текущую корректность индексации и safe-by-default модель продукта.
- Ожидаемый результат в 1-2 предложениях: Для измененных файлов scan pipeline выполняет минимально необходимое число чтений с диска вместо нескольких независимых проходов на один и тот же файл. Производительность полного и инкрементального скана улучшается без изменения пользовательского поведения API/UI.

## 2. Scope
- Входит в задачу:
  - Анализ текущего scan pipeline и точек повторного чтения файлов.
  - Рефакторинг `scanner`/`hasher` слоя так, чтобы exact/similar hashes вычислялись из общего чтения файла или из единого подготовленного буфера/стрима.
  - Сохранение существующего контракта `files` / `file_hashes` и результатов exact/similar dedup.
  - Добавление тестов и минимальных измерений, подтверждающих отсутствие регрессии по корректности.
- Не входит в задачу:
  - Полная параллелизация scan pipeline между несколькими writer-процессами.
  - Замена SQLite на другую СУБД.
  - Переработка алгоритмов dedup или продуктового UX scan/review/actions.

## 3. Контекст
- Связанные документы/файлы: `backend/app/core/scanner.py`, `backend/app/core/hasher_exact.py`, `backend/app/core/hasher_similar.py`, `backend/tests/core/test_core_pipeline.py`, `docs/architecture.md`, `docs/specification.md`.
- Текущие ограничения окружения (DSM6, Docker, пути NAS и т.д.): Целевой runtime остается `DSM6 + Docker + SQLite`; в ops-документации уже зафиксирован риск `database is locked`, поэтому оптимизация должна избегать роста числа конкурентных writer'ов.
- Зависимости/интеграции: CORE-01, CORE-02, CORE-03, current scan orchestrator, file hash persistence, regression tests.

## 4. Требования
- Функциональные требования:
  - Для измененного файла exact и similar hashes должны вычисляться без трех независимых полных чтений одного и того же файла.
  - Инкрементальная логика `changed / unchanged / missing` должна сохранить текущую семантику.
  - Формат хранения хэшей и downstream-контракты dedup/grouping не должны измениться.
  - Решение должно быть совместимо с текущим scan orchestrator и worker flow без изменения API-контрактов.
- Нефункциональные требования (производительность, безопасность, UX):
  - Оптимизация должна снижать избыточный I/O и не увеличивать существенно пиковое потребление RAM на больших файлах.
  - Решение должно оставаться детерминированным: одинаковый входной набор файлов дает те же hash values и те же dedup-группы, что и до оптимизации.
  - Приоритет: корректность и устойчивость индекса выше, чем максимальная скорость.
- Ограничения по безопасности данных:
  - Во время скана допускается только чтение NAS-файлов; оптимизация не должна добавлять destructive действий.
  - Нельзя полагаться на небезопасное масштабирование числа SQLite writer'ов как способ ускорения.

## 5. Критерии приемки
1. Для измененного файла scan pipeline больше не делает три независимых полных чтения для `blake3_full`, `dhash64` и `phash64`.
2. Существующие сценарии полного и инкрементального скана сохраняют корректность индексации, dedup-групп и auto-primary scoring.
3. Измерения на контрольном наборе или тестовом harness подтверждают снижение избыточного чтения и отсутствие функциональной регрессии.

## 6. Проверки и тесты
- Какие проверки обязательны:
  - Проверка scan pipeline на unchanged/changed/missing сценарии.
  - Проверка стабильности exact/similar hash values после рефакторинга.
  - Сравнение результатов dedup до/после на фиксированном наборе файлов.
- Какие тесты нужно запустить:
  - `PYTHONPYCACHEPREFIX=/tmp/python-pycache python3 -m compileall backend/app backend/tests`
  - `PYTHONPATH=. /tmp/nas-diff-venv/bin/python -m pytest -q backend/tests/core/test_core_pipeline.py backend/tests/api/test_qa_02_regression.py`
  - При наличии отдельного benchmark/harness: локальный замер времени и/или числа чтений на контрольном датасете.
- Что считается успешной валидацией:
  - Тесты проходят без изменения продуктового поведения, а измерения подтверждают, что чтение одного файла консолидировано и не размножается между hash-функциями.

## 7. Риски
- Основные риски:
  - Случайная смена hash semantics при объединении логики чтения.
  - Рост потребления памяти, если оптимизация будет строиться на полном буферизации больших файлов.
  - Скрытая регрессия в incremental scan при смешении I/O и DB update flow.
- Что делать при отклонении/ошибке:
  - Предпочесть streaming/shared-reader дизайн полному `read_bytes()` буферу для больших файлов.
  - Сохранить точку rollback на уровне hasher API и сравнить результаты до/после на фиксированном датасете.
  - При споре между скоростью и устойчивостью выбирать более безопасный вариант с одним DB writer.

## 8. Уровень неопределенности
Оценка `U = (R + T + D + S) / 4`:
- `R` (requirements): 0.06
- `T` (technical): 0.10
- `D` (data/environment): 0.10
- `S` (safety impact): 0.06
- Итог `U`: 0.08

Если `U > 0.1`, перед реализацией нужны уточнения.

## 9. Формат результата
- Какие артефакты ожидаются (код, конфиги, docs): изменения scan/hash модулей, тесты/benchmark harness при необходимости, обновление docs при изменении архитектурных оговорок по pipeline.
- Какой отчет нужен в финале: краткое описание выбранного подхода к консолидации чтения, результаты проверок, оценка эффекта по I/O/времени и оставшиеся ограничения.
