# UI-04

## 1. Задача
- Краткое название: Таблица jobs, status-row и человекочитаемые имена
- Цель (что должно измениться в системе): Сделать мониторинг scan jobs управляемым: таблица jobs, выбор строки, детальный статус в отдельной панели/строке.
- Ожидаемый результат в 1-2 предложениях: Jobs отображаются как операционный журнал; по клику на job оператор видит детальный статус и метрики.

## 2. Scope
- Входит в задачу: Таблица jobs, фильтры/сортировка, detail row/panel по клику, UI-нейминг jobs (`mode + sequence + time`).
- Не входит в задачу: Экспорт отчетов и внешняя аналитика.

## 3. Контекст
- Связанные документы/файлы: `frontend/src/pages/DashboardPage.jsx`, `tasks/API-03.md`, `docs/specification.md`.
- Текущие ограничения окружения (DSM6, Docker, пути NAS и т.д.): Один оператор, локальный UI.
- Зависимости/интеграции: API-03 (`GET /scan/jobs`), API-02 (`GET /scan/jobs/{job_id}`).

## 4. Требования
- Функциональные требования:
  - Таблица jobs с колонками: display name, mode, status, requested_at, finished_at, groups/files counters.
  - Клик по строке job -> detail-row/detail-panel с error_message, roots, метриками.
  - Человекочитаемое имя job в UI: `SCAN-<MODE>-<SEQ>` + timestamp.
- Нефункциональные требования (производительность, безопасность, UX): Таблица быстро работает на истории 1000+ jobs.
- Ограничения по безопасности данных: UI-нейминг не влияет на реальный `job_id` и idempotency.

## 5. Критерии приемки
1. Jobs читаются и отображаются таблицей.
2. Детали конкретного job появляются по клику без перехода на отдельную страницу.
3. Пользователь видит осмысленные имена job и может найти нужный запуск быстрее.

## 6. Проверки и тесты
- Какие проверки обязательны: UI integration tests для table + detail row.
- Какие тесты нужно запустить: Component/e2e smoke jobs table flow.
- Что считается успешной валидацией: Полный сценарий выбора job и просмотра статуса проходит без ручных обходов.

## 7. Риски
- Основные риски: Путаница между display name и техническим `job_id`.
- Что делать при отклонении/ошибке: В detail-view всегда показывать и display name, и оригинальный `job_id`.

## 8. Уровень неопределенности
Оценка `U = (R + T + D + S) / 4`:
- `R` (requirements): 0.08
- `T` (technical): 0.09
- `D` (data/environment): 0.07
- `S` (safety impact): 0.05
- Итог `U`: 0.07

Если `U > 0.1`, перед реализацией нужны уточнения.

## 9. Формат результата
- Какие артефакты ожидаются (код, конфиги, docs): Таблица jobs + detail panel + UI tests.
- Какой отчет нужен в финале: Демонстрация UX-сценария и результаты test-run.
