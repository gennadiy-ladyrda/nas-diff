# API-03

## 1. Задача
- Краткое название: Каталог scan jobs и безопасное удаление
- Цель (что должно измениться в системе): Добавить API для списка scan jobs и контролируемого удаления job-метаданных.
- Ожидаемый результат в 1-2 предложениях: UI получает список jobs с фильтрацией/пагинацией, оператор может удалять ненужные jobs без воздействия на реальные файлы NAS.

## 2. Scope
- Входит в задачу: `GET /api/v1/scan/jobs`, `DELETE /api/v1/scan/jobs/{job_id}` (safe-first policy), валидация зависимостей (groups/actions).
- Не входит в задачу: Массовое удаление всех исторических jobs одной операцией.

## 3. Контекст
- Связанные документы/файлы: `docs/specification.md`, `backend/app/api/routes_scan.py`, `backend/app/db/repositories/scan_jobs.py`.
- Текущие ограничения окружения (DSM6, Docker, пути NAS и т.д.): Один локальный пользователь, SQLite, RQ worker.
- Зависимости/интеграции: UI-04 (таблица jobs), QA-02.

## 4. Требования
- Функциональные требования:
  - `GET /api/v1/scan/jobs` с сортировкой по времени, пагинацией и базовыми фильтрами по статусу/режиму.
  - `DELETE /api/v1/scan/jobs/{job_id}` с safe-default (soft-delete/архивация или строгая проверка перед hard-delete).
  - Удаление job не должно удалять файлы в NAS.
- Нефункциональные требования (производительность, безопасность, UX): Стабильные ответы API для таблицы jobs в UI.
- Ограничения по безопасности данных: Запрет на операции, затрагивающие реальные файлы, только метаданные индекса.

## 5. Критерии приемки
1. UI может получить список jobs одной API-точкой.
2. Удаление job работает предсказуемо и не ломает связанные сущности.
3. Ошибки удаления (конфликты/зависимости) возвращаются в понятном формате.

## 6. Проверки и тесты
- Какие проверки обязательны: Контракты list/delete, сценарии конфликтов.
- Какие тесты нужно запустить: `pytest` API + repository тесты для jobs cleanup.
- Что считается успешной валидацией: list/delete сценарии проходят в автоматических тестах.

## 7. Риски
- Основные риски: Потеря полезного аудита при агрессивном удалении.
- Что делать при отклонении/ошибке: По умолчанию soft-delete, hard-delete под отдельным флагом и confirm.

## 8. Уровень неопределенности
Оценка `U = (R + T + D + S) / 4`:
- `R` (requirements): 0.08
- `T` (technical): 0.08
- `D` (data/environment): 0.07
- `S` (safety impact): 0.09
- Итог `U`: 0.08

Если `U > 0.1`, перед реализацией нужны уточнения.

## 9. Формат результата
- Какие артефакты ожидаются (код, конфиги, docs): API endpoint'ы, repository changes, тесты.
- Какой отчет нужен в финале: Результаты list/delete API-тестов и политика удаления job.
