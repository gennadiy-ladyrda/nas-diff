# ACT-03

## 1. Задача
- Краткое название: Simple Scan — единое действие по всем файлам последнего job
- Цель (что должно измениться в системе): Добавить на экран `Simple Scan` кнопку массового действия, применяющую выбранный тип операции ко всем релевантным файлам последнего job.
- Ожидаемый результат в 1-2 предложениях: Оператор на `Simple Scan` выбирает действие из выпадающего списка Actions и одним нажатием запускает batch по данным последнего job с безопасным confirm/preview.

## 2. Scope
- Входит в задачу: UI-контролы на `Simple Scan`, backend-агрегация file_ids по последнему job, запуск action batch (`preview -> create -> confirm`).
- Не входит в задачу: Полная переработка `Review & Actions` или удаление существующего action workflow.

## 3. Контекст
- Связанные документы/файлы: `frontend/src/pages/DashboardPage.jsx`, `frontend/src/api/client.js`, `backend/app/api/routes_actions.py`, `backend/app/services/action_service.py`, `docs/specification.md`.
- Текущие ограничения окружения (DSM6, Docker, пути NAS и т.д.): Безопасный режим по умолчанию (`move_to_trash`), `delete_permanent` только с усиленным подтверждением.
- Зависимости/интеграции: ACT-01, ACT-02, UI-05.

## 4. Требования
- Функциональные требования:
  - В `Simple Scan` добавить dropdown `Actions` (минимум: `move_to_trash`, `delete_permanent`; опционально `restore` при валидном сценарии).
  - Добавить кнопку общего действия: применяет выбранный action к набору файлов последнего job.
  - До выполнения обязателен preview последствий (`files_count`, `total_bytes`, `estimated_reclaimable_bytes`).
  - Для `delete_permanent` обязательны staged confirm и отдельное явное подтверждение оператора.
  - Источник файлов должен быть детерминирован: все non-primary файлы групп (`exact/similar`) последнего job в рамках текущей safe-policy.
- Нефункциональные требования (производительность, безопасность, UX): Никаких silent-fail; пользователь должен видеть, сколько файлов попадет в действие.
- Ограничения по безопасности данных: Действие по умолчанию `move_to_trash`, необратимые операции только с явным подтверждением.

## 5. Критерии приемки
1. На `Simple Scan` есть dropdown Actions и кнопка массового применения к последнему job.
2. Перед фактическим действием отображается preview с количественными последствиями.
3. Для destructive-режима подтверждение усилено и соответствует текущей safe policy.

## 6. Проверки и тесты
- Какие проверки обязательны: API/service tests на агрегацию file_ids из последнего job + UI component tests для simple action flow.
- Какие тесты нужно запустить: `pytest` (actions endpoints/services), `vitest` (Simple Scan action controls), e2e smoke.
- Что считается успешной валидацией: Batch создается и подтверждается детерминированно, без выхода за пределы последнего job.

## 7. Риски
- Основные риски: Неправильная семантика "все файлы" (включать ли primary и/или non-duplicate файлы).
- Что делать при отклонении/ошибке: Зафиксировать явную policy в API contract и UI-тексте перед реализацией.

## 8. Уровень неопределенности
Оценка `U = (R + T + D + S) / 4`:
- `R` (requirements): 0.10
- `T` (technical): 0.10
- `D` (data/environment): 0.09
- `S` (safety impact): 0.10
- Итог `U`: 0.10

Если `U > 0.1`, перед реализацией нужны уточнения.

## 9. Формат результата
- Какие артефакты ожидаются (код, конфиги, docs): UI + API/service изменения, тесты, обновление `docs/specification.md`.
- Какой отчет нужен в финале: Описание policy "какие файлы попадают в массовое действие" + результаты regression-тестов.
