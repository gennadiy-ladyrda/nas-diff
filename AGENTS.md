# AGENTS.md

Этот файл задает базовый регламент для кодового агента в репозитории `nas-diff`.
Цель: быстрый старт нового чата без повторного сбора требований и с минимальным риском ошибочных решений.

## 1. Порядок загрузки контекста (полный, но не избыточный)
На старте каждой новой задачи загружать контекст в следующем порядке.

1. Всегда читать:
- `docs/agent/startup-context.md`
- `docs/agent/operating-protocol.md`
- `TASK_BRIEF.md` (как шаблон постановки задачи)

2. Читать по задаче:
- Архитектура: `docs/architecture.md`
- Детальные требования и API: `docs/specification.md`
- Модель данных: `database/schema.sql` + `docs/database-schema.md`
- Структура и roadmap: `docs/blueprint-v1.md`

3. Не загружать лишнее:
- Не читать весь репозиторий целиком без необходимости.
- Загружать только файлы, влияющие на текущую задачу.

4. Планирование:
- При построении плана реализации опираться на структуру `TASK_BRIEF.md`.
- Если бриф неполный, агент добирает недостающее до уровня `U <= 0.1`.

## 2. Жесткие ограничения по работе
1. Перед реализацией сделать краткий анализ выполнимости:
- достаточно ли входных данных,
- есть ли технические блокеры,
- какие риски регрессий.

2. Любая потенциально опасная операция (удаление, массовое перемещение, необратимые изменения) требует явного подтверждения пользователя.

3. Любое изменение кода/DDL/конфигурации должно сопровождаться валидацией:
- минимум: синтаксическая проверка,
- по возможности: релевантные тесты,
- если тесты не запускались, явно указать это и почему.

4. По умолчанию придерживаться безопасного режима продукта:
- действие по умолчанию: `move_to_trash`,
- `delete_permanent` только после подтверждения.

## 3. Порог неопределенности для решений
Целевой порог: `U <= 0.1`.

Если `U > 0.1`, агент обязан:
1. остановить принятие рискованных решений,
2. задать уточняющие вопросы,
3. зафиксировать допущения,
4. перейти к реализации только после снижения `U` до `<= 0.1`.

## 4. Формула оценки неопределенности
Использовать быструю оценку:

`U = (R + T + D + S) / 4`

Где:
- `R` — неопределенность требований,
- `T` — техническая неопределенность реализации,
- `D` — неопределенность данных/окружения,
- `S` — неопределенность влияния на безопасность/данные.

Шкала для каждой величины: `0.0 .. 1.0`.

## 5. Формат результата по задачам
В финальном ответе всегда давать:
1. что сделано,
2. какие файлы изменены,
3. как проверено,
4. какие риски/ограничения остались,
5. следующий практический шаг.
