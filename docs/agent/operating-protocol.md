# Operating Protocol

Операционный регламент для кодового агента в `nas-diff`.

## 1. Алгоритм работы над задачей
1. `Intake`
- Сформулировать задачу в 1-2 предложениях.
- Проверить ограничения пользователя и среды.
- Использовать `TASK_BRIEF.md` как базовый шаблон постановки.

2. `Feasibility Check`
- Выполнимость: можно ли реализовать в текущем репозитории/окружении.
- Зависимости: нужны ли новые сервисы/библиотеки.
- Риски: влияние на данные, совместимость с DSM6, регрессии.

3. `Uncertainty Gate`
- Посчитать `U` по формуле из `AGENTS.md`.
- Если `U > 0.1`: задать уточняющие вопросы до порога `<= 0.1`.

4. `Execution Plan`
- Сопоставить план со структурой `TASK_BRIEF.md` (Scope, требования, критерии приемки, проверки).
- Разбить на конкретные шаги.
- Определить проверки для каждого шага.

5. `Implementation`
- Вносить изменения малыми порциями.
- Для небезопасных действий требовать явное подтверждение.

6. `Validation`
- Проверить синтаксис и связность артефактов.
- Запустить релевантные тесты/проверки.

7. `Report`
- Дать итог: изменения, проверки, ограничения, следующий шаг.

## 2. Политика тестирования
Минимально обязательно после изменений:
1. Конфиги/инфра:
- `docker compose config`.

2. SQL/DDL:
- проверка применимости схемы в `sqlite3 :memory:`.

3. Backend-код (когда появится):
- `pytest` для измененных модулей,
- минимум один happy-path сценарий для затронутой функциональности.

4. Если тесты не удалось запустить:
- зафиксировать причину,
- оценить риск,
- предложить точный шаг для воспроизведения проверки.

## 3. Политика принятия решений
1. Приоритеты:
- корректность и безопасность данных,
- затем производительность,
- затем удобство разработки.

2. Для спорных решений:
- предложить вариант A (безопасный, рекомендованный),
- предложить вариант B (быстрее/проще),
- коротко описать компромисс.

3. Запреты без подтверждения:
- необратимое удаление файлов,
- рискованные массовые операции,
- действия, способные повредить индекс/данные.

## 4. Контроль качества документации
Документация считается достаточной, если:
1. Можно запустить проект по `docker-compose.yml` и `.env.example`.
2. Понятны целевая архитектура, API-контур и схема БД.
3. Для новой задачи можно определить точку входа без дополнительного брифа.

## 5. Definition of Ready для реализации
Перед началом кодинга должны быть ясны:
1. ожидаемый результат,
2. ограничения безопасности,
3. критерии приемки,
4. тесты/проверки, которые подтвердят результат.

Если хотя бы один пункт не ясен, агент снижает неопределенность вопросами до `U <= 0.1`.
